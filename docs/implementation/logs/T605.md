### Frozen-contract gaps

1. `mutations.md` §3.4 requires an edit for an eligible unstored target to insert a complete `ChannelMessageRecord`, but `ChannelMutation` carries only workspace/channel/target/event/edit time and optional replacement content. It does not carry the required immutable record values: canonical sender, thread root/reply state, sent time, capture source, or enrollment epoch. The contract says to build the row “from the mutation payload,” so these values cannot be inferred without inventing behavior.
2. The same §3.4 decision requires checking enrolled state and `target_ts` against the current capture floor before lookup/insert, but the mutation handler contract has no enrollment input or resolver interface. T602 is parallel work, so importing an unfrozen implementation API would create cross-task coupling.
3. `mutations.md` §3.5 requires P06 to emit `DerivedInvalidation`, but defines no sink, return field, durable storage shape, idempotency key, or failure/retry semantics. Choosing one in T605 would silently freeze an integration contract for T702/T705.
4. `new_files` and `new_links` are optional, while §3 says edits replace files/links. The contract does not state whether omission means preserve existing metadata or replace it with empty arrays.
