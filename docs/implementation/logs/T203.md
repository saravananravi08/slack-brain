- Decisions/assumptions:
  - **The guard never composes a `BoundaryId`.** identity.md §4 makes composition T202's `resource-policy.ts` alone, and T202 is not merged. So identities arrive already composed (as authorization.md §2 specifies) and the guard only checks that the identity it was handed *describes the event in front of it*. A test asserts no composition appears in the module. This is what turns FR-PRV-003/004 into a structural check: a DM event presenting a `ch:` boundary, or a request presenting another user's or another channel's boundary, is denied rather than filtered later.
  - **Membership arrives as resolved boundaries, not channel IDs.** authorization.md §7 puts the network call and the fail-closed behavior in the resolver that populates `PolicySnapshot`. Modelling membership as `{ status: 'resolved', boundaries } | { status: 'unavailable' }` gives the failure case a name, so widening on failure is not expressible. Absent membership behaves as unavailable.
  - **`sender_is_deactivated` is a required field the frozen event contract does not have.** slack-event.md §2 lists `sender_is_external` and `sender_is_guest` but no deactivation flag, while D006 rule 5 and `fixtures/authorization.v1.json` both require the `deactivated_user` denial. It is declared required rather than optional on the guard's structural subset of `NormalizedEvent`: an optional field would default to "not deactivated", which is the fail-open direction. Flagged for the integrator — T402 will need to carry it on `NormalizedEvent`, or T004 will need an amendment.
  - **Envelope validation runs before the ordered rules; blank-value checks stay at step 8.** Rules 1–7 cannot be evaluated against a request whose fields are missing or mistyped. Blank-but-typed values are left to step 8 so the contract's stated rule order is preserved exactly, which is what makes the fixture's `malformed_identity` case resolve to `malformed_request` rather than to an earlier rule.
  - **An empty `approved_channel_ids` denies.** T102 already fails startup on it; the guard denies as well, so a policy that somehow reaches the guard degraded cannot read as "all channels approved" (D001).
  - **`retrievalScope` throws on a denied or empty decision** instead of returning `[]`. An empty filter reads at a retrieval call site as "no filter", which is the shape of a corpus-wide leak; a thrown `AuthorizationScopeError` is the fail-closed direction.
  - **`AuthorizationDecision` carries an extra `gate` field** beyond the three in authorization.md §2. It is additive and structurally compatible with the contract and with T104's `ChannelAuthorizationDecision`; it exists so a denial can be logged with its gate without the caller re-deriving it.
  - **`dm_shared_knowledge_disabled` is never emitted.** It is in the contract's `DenyReason` union but no ordered rule produces it: under D002 a DM read is *allowed* with a narrowed scope, not denied. It is kept in the union for contract fidelity and classified as user-scoped; the channel adapter maps it to a silent denial so an unexpected value cannot produce a misleading reply.
  - **The D002-enabled branch is implemented but unreachable.** T102 types `GIST_DM_SHARED_KNOWLEDGE` as the literal `false`, and a test asserts `parseConfig` rejects `true`. The branch is covered by tests so a future re-approval starts from a known shape, and so a premature flip fails an expectation rather than leaking. It is not enabled anywhere in this branch.
  - **The security module imports nothing from `src/mastra` at runtime.** T104's port shape is declared structurally here and pinned by a type-level assertion in the test, so the dependency runs one way only. `policy.ts` takes a type-only import of T102's `Config`.
