### Design decisions taken (and why), all within accepted decisions

1. **Additive set, superseding nothing.** The channel-memory set superseded four v1 clauses; this one must not. Supervision sits *after* capture and adds a layer. `README.md` §1 states the three places it extends an existing rule (dedicated automation path, cooldown separation, Linear as a second configured trusted identity) and shows each leaves the underlying rule verbatim.
2. **`ActorClass` is derived, not a seventh `sender_class`.** Channel memory owns the six-member sender union; widening someone else's type to add `linear` would put a supervisor concern into the capture layer. The supervisor computes its own class from `sender_class` + configuration + the authorization decision.
3. **Two configurations disagreeing fails towards capture-only.** A message whose `sender_class` is `kilo` (from the normalizer's config) but whose IDs do not match the supervisor's `TrustedAutomationConfig` resolves to `unknown_automation`. Pinned by `kilo_sender_class_without_matching_config_is_unknown`.
4. **`gist_self` is `evaluated: 'never'`, not `'no'`.** The three-valued eligibility exists so the matrix can express "no configuration or later decision may turn this on" (GS-FR-040) distinctly from "not enabled here".
5. **`ready → dispatched` only on confirmed delivery.** There is no state meaning "sent, we think". A failed dispatch leaves the workflow in `ready` and increments failures (GS-FR-042); `ready` deliberately has no self-transition so a failure is recorded as a failure.
6. **`dispatched` is reachable only from `ready`.** One gate to every external instruction, so the checkpoint has exactly one place to be enforced. A review fix therefore routes `changes_requested → ready`, not straight to `dispatched`.
7. **Replayed source events are `idempotent`, not `rejected`.** Compare-and-set returns a third outcome so a retried or replayed event converges on one transition without the caller inventing a recovery path (GS-FR-014 + GS-FR-020 together).
8. **`context_refs` are opaque runtime handles, not `MessageKey`s.** A `MessageKey` is `workspace_id/channel_id/message_ts`, so letting the model emit one would put Slack identifiers into a validated action and carve an exception into GS-INV-10. The runtime issues `ctx_<n>` handles from the bounded context it already assembled and resolves them back, dropping anything outside the binding. **This was a mid-task correction:** the first draft used `MessageKey[]` and the schema test immediately exposed the contradiction.
9. **Limits live on the workflow record, not in global config.** A config change must not retroactively widen a running workflow, and a restart must not pick up a laxer bound than the work started under (GS-NFR-007). `max_in_flight_actions` is fixed at 1 because it is GS-FR-024 expressed as a limit; making it tunable would make an invariant a setting.
10. **Limit precedence is lifetime → inactivity → failures → turns.** Timeouts terminate, turn/failure limits pause. When both hold the terminal answer is correct: nothing is going to arrive for a workflow past its lifetime.
11. **An unreconcilable in-flight dispatch asks a human.** Re-sending risks a duplicate instruction, and a duplicate instruction to a coding bot is a duplicate PR. Reconciliation consults Gist's own outgoing record first, since the send path persists outgoing messages directly and does not depend on Slack echo behavior.
12. **Requesting approval for a non-gated action is a violation, not caution.** Redundant confirmation trains owners to approve without reading, which is how a genuinely gated action gets waved through (GS-FR-006/D025). `mayRequestApproval` returns false for every non-gated class and is asserted for all ten work classes.
13. **An unmeasured compatibility field is a NO-GO.** Rule 6 of `compatibility.md` §4. The whole point of the spike is that the protocol stops assuming, so a gap is not neutral. §5 lists the seven clauses whose wording depends on measurement, so T803 amends a known list rather than rediscovering the dependencies.
14. **Reopen is a new linked record, not a terminal-state transition.** Recorded as an explicit assumption in `workflow-state.md` §2.4 and as an open item in `requirements-map.md`, because re-enterable terminal states would let a replayed completion resurrect finished work (GS-FR-020). A linked record can be collapsed into a transition later; a resurrection cannot be un-shipped.

### 1. Clear-assignment progress gap → `ContinuationEvent`

`actions.md` §2 kept creation and dispatch in separate turns but scheduled nothing to take the second one, so a clear authorized assignment could sit in `draft` until somebody typed again — contradicting GS-FR-006 and PRD acceptance scenario 1.

Frozen a durable, runtime-owned continuation (`actions.md` §2.1–§2.3, `events.md` §2.1, `workflow-state.md` §3.4):

- A committed transition into a Gist-expected state (`draft`, `ready`, `changes_requested`) **enqueues one continuation in the same atomic commit as the transition**. One write, not two: any gap between "this workflow now expects Gist" and "something is scheduled to act as Gist" is a window in which a crash strands the work silently.
- It enters the admission pipeline at step 6 (correlate), is serialized on its workflow in the same queue as Slack events, re-reads durable state after the queue, and produces at most one externally visible action under its own claim.
- The walk is `human message → draft → ready → dispatched`: **one Slack event, one visible action, no confirmation asked**.

Five bounds, and the third is the one that makes the rest unnecessary in practice: only Gist-expected states enqueue; at most one pending per workflow; **the transition table contains no cycle among Gist-expected states** (`draft→ready` and `changes_requested→ready` are the only edges between two of them, and neither `draft` nor `ready` self-transitions), so the longest chain is two continuations; a continuation consumes a turn like any other event, so `max_turns` bounds it; and a failed dispatch commits no state change, so it enqueues nothing — retry stays `dispatch.md` §3.3 rather than becoming an internal turn loop.

**Not a hole in GS-INV-05.** A continuation is a state-machine step whose only inputs are the durable record and its limits. It carries no actor, no message, and no content, and can never be constructed from a Slack message, bot content, or model output. Stated in `actions.md` §2.3 and in GS-INV-05 itself.

### 2. Model-controlled timeout → the envelope splits

`ExpectedResponse.response_deadline_ms` sat in the model-supplied envelope while `workflow-state.md` §7.4 forbade content from extending a timeout. A model-chosen deadline was exactly that extension, arriving through the one field nobody was checking.

`actions.md` §5 now splits `InstructionEnvelope` into `ModelInstruction` (`work_class`, `objective`, `scope`, `acceptance`, `context_refs`) and `RuntimeInstruction` (`workflow_marker`, `expected_response`, `prohibitions`). The line is *the work* versus *the protocol*. A model action carrying any runtime field is rejected with `runtime_controlled_field_present` — rejected, not merged and not silently dropped, because a silent drop makes a model that reaches for policy invisible.

`response_deadline_ms` is derived: `min(inactivity_timeout_ms, remaining_lifetime_ms)`, and a non-positive result **dispatches nothing** and times the workflow out instead, rather than promising a bot a window that ends after the workflow does. GS-FR-025 is still satisfied by the *composed* envelope; only the model's contribution narrowed.

### 3. Ambiguous retry could duplicate a dispatch → three delivery outcomes

`confirmDelivery` mapped a timeout to `failed`, and `failed → pending` permitted a retry. That retried a post that might still have been in flight — one instruction delivered twice, which for a coding bot is a duplicate pull request. It was also the exact behavior `compatibility.md` §4 refuses to accept *from a bot*.

`dispatch.md` §3.1–§3.3 adds `DeliveryOutcome = delivered | definitive_failure | indeterminate`:

- `definitive_failure` only where Slack refused the call before accepting it (`slack_permission_denied`, `slack_rate_limited`, `slack_invalid_request`, `destination_unresolved`).
- Everything else — timeout, `slack_transport_error`, and a response with no identity, no error and no timeout — is `indeterminate`, and the checkpoint **stays `in_flight`**.
- Reconciliation then decides, and it is now one function with two callers (inline after an indeterminate outcome, and at restart) because a timeout mid-run and a crash mid-send leave the same question behind.
- Proven non-delivery (readable thread, instruction absent) becomes `failed` and may retry. Unresolved stays `in_flight` and moves the workflow to `waiting_human` with `dispatch_unreconciled` — **no send**. Not `failed`, which would make it retryable; not `delivered`, which nothing proved; not `abandoned`, which would deny an instruction that may be live at the far end.

`slack_transport_error` moved out of the retryable group and into a new "reconciles" group. It reads like a transport hiccup and is the one error class that cannot say whether the post landed.

### 4. Unbound visible-action claim gap → the claim is event-global

`ActionClaimKey` was `wf:<workflow_id>|ev:<source_event_key>`, but two externally visible actions carry no `workflow_id`: an unmatched trusted-bot notification (`events.md` §4.3) and ordinary assistance outside any workflow. Those had no key to claim, so a Slack retry could have produced a second notification and GS-FR-024 held only for the bound half of the traffic.

The key is now `ev:<source_event_key>`, with the workflow recorded as claim metadata for audit. It is strictly stronger and costs nothing, because one event correlates to at most one workflow (a thread holds at most one non-terminal workflow). `SourceEventKey` covers Slack `MessageKey`s and continuation keys alike, so fix 1's internal turns are bounded by the same rule.

### 5. Compatibility outcome overconstraint → `stable_text` is GO

`distinguishes_outcomes` required a *structural* success/failure difference and made everything else NO-GO. That was a T801 overconstraint, not a product requirement: GS-FR-028 asks Gist to interpret Kilo/Linear replies and D024/GS-FR-017 route trusted replies into evaluation precisely so it can. A bot that reports "done" reliably in English would have failed the Slack-only path over a formatting preference.

Replaced with `outcome_distinguishability = structured | stable_text | unreliable | unknown` (`compatibility.md` §2.1). `structured` and `stable_text` are both GO; only `unreliable` and `unknown` block. `stable_text` carries a sample floor of 3 (blocking reason `insufficient_samples`) — the looser evidential standard gets the tighter sampling requirement, because "the wording is stable" is a claim about repetition and cannot be made from one reply.

**What did not soften:** §2.2 states that distinguishability classifies *evidence* and never confers authority. A textual completion signal still has to correlate on the full binding, pass compare-and-set, and obtain a version-bound human approval for anything gated. Prose saying "approved" or "you may merge" changes nothing under any value of this field. Pinned by `prose_is_not_authority` in the fixture and asserted against GS-INV-07.
