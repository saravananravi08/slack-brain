# T609 — Proactive action mode

## Outcome

Implemented D021 for opt-in proactive action on live, unaddressed channel messages.

- Added `GIST_PROACTIVE_CHANNELS` with empty/off default and validated comma-separated channel IDs.
- Added `GIST_PROACTIVE_COOLDOWN_MS` with default `60000`.
- Added a bounded relevance gate using T704 channel context and one deterministic OpenAI JSON-schema classification call.
- Authorized candidates before context retrieval/classification.
- Routed `act=true` through existing `channel.handlers.onNewMention`, preserving thread routing and response behavior.
- Reused delivery dedup and kept mention/edit-trigger paths out of proactive classification.
- Added serialized per-channel in-memory cooldown state.
- Classifier/context failures fail closed and emit only a content-free error class.

## T609b — D022 default-all handoff

Implemented D022 in `14f2233` (`feat(T609b): proactive defaults to all enrolled channels per D022`).

- Empty/unset `GIST_PROACTIVE_CHANNELS` now enables proactive mode for every enrolled channel; a non-empty list remains restrictive.
- Empty-list checks consult the joined-channel enrollment registry and fail closed on lookup failure.
- P06 always registers the ambient `onNewMessage` route when a proactive evaluator is composed.
- Human, unaddressed, enrolled, authorized messages alone reach evaluation. Bot/app/Gist exclusion, delivery dedup, per-channel cooldown, and classifier fail-closed behavior remain intact.
- Every reached gate emits `channel.proactive.gate.evaluated` with `channelAlias` only. No message text or sender data is logged.

### Live no-fire root cause

The running `dist/src/index.js` process had no `GIST_PROACTIVE_CHANNELS` entry in `/proc/<pid>/environ`. Under D021, parsing an absent value produced `[]`, and emitted `dist/src/mastra/channels/slack.js` registered `onNewMessage` only when `proactive.hasChannels` was true. Live unaddressed messages therefore took the raw capture path but never the Chat ambient callback that invokes the gate. The fixed build always registers that callback and resolves an empty restriction list through enrollment.

## T609c — live ambient-path proof and diagnostics

Implemented in `b938523` (`feat(T609c): wire proactive gate into live ambient path`).

### Exact root cause

The live gate path was present, but production channel logging was disabled:

- `src/mastra/index.ts` constructed `createLiveSlackChannel(...)` without a `logger`.
- `src/mastra/channels/slack.ts` therefore selected `const logger = options.logger ?? NOOP_LOGGER`.
- Gate evaluation, authorization failures, and classifier failures could occur with zero operational log lines. A classifier `act=false` also intentionally produces no Slack response, making a working gate indistinguishable from an unwired one.

T609c supplies a production `ConsoleLogger`, logs proactive activation after Slack initialization and enrollment replay, and emits content-free counters at raw receipt, capture routing, ambient callback, eligibility, gate evaluation, and gate decision. Authorization/classifier failures are now visible without logging message or sender data.

The installed Slack adapter was traced end to end: Socket Mode `slack_event` → `routeSocketEvent(events_api)` → `processEventPayload` → `handleMessageEvent` → Chat `processMessage` → `onNewMessage` ambient handler. A regression test now injects a synthetic event through this real Socket Mode adapter route instead of only calling the direct payload seam.

### Live evidence

The rebuilt process ran from the T609 worktree, connected through Slack Socket Mode, completed enrollment replay, and reported proactive mode active with two restricted channels. A new unaddressed human message produced all six stages (channel alias redacted here):

1. `channel.proactive.path.raw_received` — count 1
2. `channel.proactive.path.ambient_received` — count 1
3. `channel.proactive.candidate.eligible` — count 1
4. `channel.proactive.path.capture_routed` — count 1, trigger `proactive`
5. `channel.proactive.gate.evaluated` — count 1
6. `channel.proactive.gate.decided` — count 1, `act=false`

No response posted because the relevance classifier returned `act=false`; this was a policy decision, not a routing failure. A live-log field scan found no `text`, `user`, `sender`, or `message` fields in proactive lines. The trace contained only scope/count, channel alias, trigger, and boolean decision metadata.

Operational correction to T609b: `/proc/<pid>/environ` is not authoritative for variables loaded by Node's `--env-file` in this environment. T609c startup configuration proved two restricted channels were parsed even while `/proc` showed the variable absent.
