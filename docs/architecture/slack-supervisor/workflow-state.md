# Contract — durable workflow record and state transitions

- **Contract set:** slack-supervisor
- **Contract version:** 1.0.0
- **Owner:** T801 (frozen); consumers T901, T905, T906
- **Implements:** D025, D026, D028
- **Satisfies:** GS-FR-012, GS-FR-013, GS-FR-014, GS-FR-015, GS-FR-016, GS-FR-029, GS-FR-030, GS-FR-038, GS-FR-039, GS-NFR-002, GS-NFR-005, GS-NFR-007

Channel memory explains what was said. This record determines what is active, who owns it, which
actor is expected, what action is pending, whether an approval exists, and whether the work is
still allowed to continue. Only this record authorizes a transition or a dispatch (D026).

## 1. `WorkflowRecord` (GS-FR-012)

```text
WorkflowRecord
  workflow_id            string     # collision-resistant, runtime-generated, never model-supplied
  contract_version       string
  owner_user_id          string     # exact Slack U…; the requesting authorized human
  workspace_id           string
  channel_id             string
  thread_root_ts         string     # verbatim Slack ts
  boundary_id            BoundaryId
  thread_id              ThreadId
  objective_message_key  MessageKey # reference into channel memory; never the objective text
  state                  WorkflowState                 # §2
  expected_actor         ExpectedActor                 # §2.2
  pending_action_id      string | null
  pending_action_version integer | null                # §3.2
  approval_state         ApprovalState                 # approvals.md §3
  turn_count             integer
  consecutive_failures   integer
  limits                 WorkflowLimits                # §7
  created_at             timestamp
  updated_at             timestamp
  last_activity_at       timestamp
  timeout_at             timestamp | null
  completed_at           timestamp | null
  outcome_class          OutcomeClass | null           # §6.2
  reopened_from          string | null                 # §2.4
```

Every field is an ID, a class, a count, or a time. The objective, the clarifications, the
instructions, and the bot replies live in channel memory and are referenced by `MessageKey`. A
workflow record that carried conversation text would duplicate the evidence store, drift from it on
edit, and put message content into a second retention domain (GS-NFR-004).

`workflow_id` is generated by the runtime and is **collision-resistant**. It is not derived from a
Slack timestamp, not a channel-scoped counter, and never supplied by a model or read out of message
content.

## 2. States

### 2.1 The thirteen states (GS-FR-013)

```text
WorkflowState =
  'draft' | 'clarifying' | 'ready' | 'dispatched' | 'running' | 'waiting_human' |
  'waiting_bot' | 'reviewing' | 'changes_requested' |
  'completed' | 'failed' | 'cancelled' | 'timed_out'
```

| State | Meaning | Who is expected to act next |
|---|---|---|
| `draft` | A work intent has been recognised; the record exists and is not yet dispatchable | Gist |
| `clarifying` | Gist asked the owner for a materially missing detail | the owner |
| `ready` | Enough is known to dispatch; no confirmed delivery yet | Gist |
| `dispatched` | An instruction was **confirmed delivered**; no bot turn yet | the expected bot |
| `running` | The expected bot has produced at least one reply and work is in progress | the expected bot |
| `waiting_bot` | A follow-up was delivered and the next bot turn is outstanding | the expected bot |
| `reviewing` | A fresh review instruction was delivered and its result is outstanding | the reviewing bot |
| `changes_requested` | Review returned findings; a fix has not yet been dispatched | Gist |
| `waiting_human` | An approval, a decision, or a limit stop needs a human | the owner or approver |
| `completed` | Terminal. Acceptance condition met | nobody |
| `failed` | Terminal. Failure recorded | nobody |
| `cancelled` | Terminal. An authorized human cancelled it | nobody |
| `timed_out` | Terminal. Inactivity or lifetime limit reached | nobody |

The four terminal states are `completed`, `failed`, `cancelled`, `timed_out`. They have **no
outgoing transitions** (§2.4).

### 2.2 `ExpectedActor`

```text
ExpectedActor = 'gist' | 'human' | 'kilo' | 'linear' | 'none'
```

`expected_actor` is what `events.md` §4.2 check 4 compares against. It is set by the transition that
produces the state, never inferred from the last message seen. Terminal states carry `none`.

Three states carry `gist`: `draft`, `ready`, and `changes_requested`. In those the workflow is
waiting on Gist and on nobody else, so a committed transition into one of them enqueues a
continuation in the same commit (§3.4). That is what stops a clear assignment from sitting in
`draft` until somebody happens to type again.

### 2.3 Dispatch never advances state on hope (GS-FR-042)

`ready → dispatched` happens **only** on a confirmed delivery. There is no state whose meaning is
"we think we sent it". What happens otherwise depends on which of the three outcomes in
`dispatch.md` §3.1 the attempt produced, and the difference matters:

| Attempt outcome | Workflow | Failure counter |
|---|---|---|
| `delivered` | `ready → dispatched` | reset on the next progress transition |
| `definitive_failure` — Slack rejected the post before accepting it | stays `ready` | `consecutive_failures` increments (`dispatch.md` §4) |
| `indeterminate` — timeout, transport error, or a silent response | stays `ready`, but the checkpoint stays `in_flight` and **no retry is scheduled**; reconciliation decides, and an unresolved one moves the workflow to `waiting_human` with `dispatch_unreconciled` | not incremented; nothing has been established to count |

An ambiguous attempt is not a failure, and treating it as one is what would license a second send.
Only a definitive pre-acceptance rejection proves the instruction was never published.

### 2.4 Terminal states are final; reopen creates a new workflow

Once terminal, a record is immutable except for append-only audit rows. PRD §5.1 gives an authorized
human the power to *reopen* work; this set implements that as a **new** `WorkflowRecord` whose
`reopened_from` names the terminal one, not as a transition out of a terminal state.

> **Assumption recorded by T801.** The PRD names reopen as a human power (§5.1) but GS-FR-013 lists
> no `reopened` state and GS-FR-014 requires transitions to be compare-and-set. Making terminal
> states re-enterable would mean a replayed completion event could resurrect finished work, which
> GS-FR-020 forbids. A new linked record is the reading that satisfies both, and it is the safer one
> if the product owner later intends something else — a linked record can be collapsed into a
> transition, but a resurrection cannot be un-shipped. Flagged for T803 and the product owner.

## 3. Transitions

### 3.1 The legal transition table (GS-FR-014)

Rows are the current state; each cell lists every legal next state. Anything not listed is illegal
and must be rejected, not clamped or coerced.

| From | Legal next states |
|---|---|
| `draft` | `clarifying`, `ready`, `waiting_human`, `cancelled`, `failed`, `timed_out` |
| `clarifying` | `clarifying`, `ready`, `waiting_human`, `cancelled`, `failed`, `timed_out` |
| `ready` | `dispatched`, `waiting_human`, `cancelled`, `failed`, `timed_out` |
| `dispatched` | `running`, `waiting_bot`, `reviewing`, `waiting_human`, `completed`, `failed`, `cancelled`, `timed_out` |
| `running` | `running`, `waiting_bot`, `reviewing`, `waiting_human`, `completed`, `failed`, `cancelled`, `timed_out` |
| `waiting_bot` | `running`, `waiting_bot`, `reviewing`, `waiting_human`, `completed`, `failed`, `cancelled`, `timed_out` |
| `reviewing` | `reviewing`, `changes_requested`, `waiting_human`, `completed`, `failed`, `cancelled`, `timed_out` |
| `changes_requested` | `ready`, `waiting_human`, `cancelled`, `failed`, `timed_out` |
| `waiting_human` | `ready`, `clarifying`, `running`, `waiting_bot`, `reviewing`, `completed`, `cancelled`, `failed`, `timed_out` |
| `completed` | — |
| `failed` | — |
| `cancelled` | — |
| `timed_out` | — |

Notes on the shape, because each is a decision rather than an accident:

- **`dispatched` is only reachable from `ready`.** Every path to an external instruction goes
  through one gate, so `dispatch.md` §2 has exactly one place to enforce the checkpoint.
- **`changes_requested → ready`, not `changes_requested → dispatched`.** A fix is a new action with
  a new version, and it re-enters the same dispatch gate. Review findings never shortcut it.
- **`waiting_human` can return to `clarifying`.** A human answering with a further question is
  ordinary, and forcing it through `ready` would falsely claim the workflow is dispatchable.
- **Self-transitions exist only where progress is genuinely repeatable**: `clarifying` (a second
  question), `running` (successive progress replies), `waiting_bot` (a second follow-up), and
  `reviewing` (interim review output). `ready → ready` is deliberately absent so a failed dispatch
  is recorded as a failure rather than as a transition.

### 3.2 Every transition is compare-and-set (GS-FR-014, GS-NFR-002)

A transition commits only if, at write time, the durable record still matches the expectation the
decision was made against:

```text
TransitionRequest
  workflow_id
  expected_state              # must equal the stored state
  expected_action_version     # must equal the stored pending_action_version (null-equal allowed)
  next_state
  next_expected_actor
  source_event_key            # the event that justifies this transition
  action_id | null
  reason_class
```

Failure modes and their required outcomes:

| Condition | Outcome |
|---|---|
| `expected_state` ≠ stored state | rejected, `state_mismatch`; no write, no dispatch |
| `expected_action_version` ≠ stored version | rejected, `version_mismatch` (a stale decision) |
| `next_state` not in the §3.1 row for the stored state | rejected, `illegal_transition` |
| stored state is terminal | rejected, `terminal_workflow` |
| `source_event_key` already produced a committed transition for this workflow | rejected, `duplicate_source_event`; **idempotent success** — the caller observes the already-committed result rather than an error |
| all checks pass | committed; `updated_at` and `last_activity_at` advance; `turn_count` increments per §7.2 |

The last row is what makes a retried or replayed event safe: the same event applied twice converges
on one transition, and the second attempt is not an error the caller has to invent a recovery for
(GS-FR-014, GS-FR-020).

### 3.3 Who may request which transition

| Transition class | Requestable by |
|---|---|
| `cancelled` from any non-terminal state | the owner, or a configured approver acting on the owner's workflow |
| `waiting_human → ready` on approval grant | the owner or configured approver only (`approvals.md` §3) |
| material redirect (new objective, new logical target, widened scope) | the owner only; produces a new action version |
| ownership transfer | recorded policy action by the owner or a configured approver (`approvals.md` §4) |
| every other transition | Gist, from an evaluated event |

No transition in any class may be requested by `kilo`, `linear`, `unknown_automation`,
`unauthorized_human`, or `gist_self` (`identity.md` §3.1). A trusted bot event *causes* Gist to
request a transition; it never requests one itself, and the requester recorded in the audit row is
Gist.

### 3.4 A transition into a Gist-expected state enqueues its own next turn

Part of the same atomic commit as the transition, not a follow-up write:

```text
if next_expected_actor == 'gist' and next_state is not terminal:
    enqueue ContinuationEvent(workflow_id, continuation_seq = pending_seq + 1)
```

Idempotent on `(workflow_id, continuation_seq)`, and refused while a continuation for this workflow
is already pending. `actions.md` §2.1 defines the event and §2.2 the five bounds that keep the
mechanism finite; the reason it belongs in the transition's commit rather than after it is that any
gap between "the workflow now expects Gist" and "something is scheduled to act as Gist" is a window
in which a crash strands the work silently. Making it one write removes the window instead of
narrowing it.

A transition into `clarifying`, `waiting_human`, `dispatched`, `running`, `waiting_bot`,
`reviewing`, or a terminal state enqueues nothing: those states are waiting on somebody else, and a
continuation there would be a poll rather than a step.

## 4. Restart and recovery (GS-FR-015, GS-NFR-002)

On process start:

1. Load every workflow in a non-terminal state.
2. Re-arm inactivity and lifetime timers from `last_activity_at`, `created_at`, and `limits` —
   timers are **derived** from durable timestamps, never from in-memory state, so a restart cannot
   silently extend a deadline (GS-NFR-007).
3. Reconcile any action left in a non-terminal delivery state per `dispatch.md` §5.
4. Reload every pending `ContinuationEvent` and process it exactly once. "Exactly once" rests on the
   continuation's own **consumption claim** and on the transition compare-and-set for its
   `event_key` (`actions.md` §2.4) — not on the external-action claim, which a silent continuation
   never takes.
5. Do **not** re-send any instruction whose delivery was confirmed, and do not re-run any completed
   transition. Recovery replays state, not effects.

A workflow whose in-flight action cannot be reconciled moves to `waiting_human` with reason class
`dispatch_unreconciled`. Asking a human is the correct answer when the alternative is guessing
whether an external instruction was already delivered.

## 5. Implementation-then-review lifecycle (GS-FR-029, GS-FR-030)

When implementation work produces a pull request and review is requested or policy-required:

1. The implementation result moves the workflow to `running` or `waiting_bot`, never to
   `completed`. A PR URL is a result, not an acceptance.
2. A **fresh** review instruction is dispatched as a new action with its own version. The reviewing
   turn may not reuse the implementing action's context as if it were an independent review
   (GS-FR-029). Where the trusted bot supports it, the review instruction requests a fresh session;
   where it does not, `compatibility.md` §3 records that limitation and T803 decides whether the
   path stays GO.
3. Review output routes to `changes_requested` when findings exist, and from there to `ready` for a
   fix action.
4. `completed` requires the configured acceptance condition — review acceptance, or the explicitly
   recorded acceptance criteria from the original assignment. The presence of a PR reference alone
   never satisfies it (GS-FR-030).

## 6. Audit and outcome

### 6.1 `TransitionRecord` (GS-NFR-005)

Every committed transition appends one immutable row:

```text
TransitionRecord
  transition_id
  workflow_id
  prior_state
  next_state
  prior_expected_actor
  next_expected_actor
  event_class            # events.md §3
  actor_class            # identity.md §1
  action_class | null    # actions.md §1
  action_id | null
  action_version | null
  reason_class
  outcome                # 'committed' | 'rejected'
  occurred_at            # coarse; second precision is sufficient
```

Content-free by construction: there is no field a message body could occupy. Rejected transitions
are recorded too — a rejection is the evidence that a guard fired.

### 6.2 `OutcomeClass`

```text
OutcomeClass =
  'accepted' | 'rejected_by_human' | 'cancelled_by_human' |
  'bot_failure' | 'dispatch_failure' | 'limit_turns' | 'limit_failures' |
  'timeout_inactivity' | 'timeout_lifetime' | 'compatibility_blocked' | 'internal_error'
```

Set exactly once, on entry to a terminal state, alongside `completed_at`.

## 7. Limits and bounded autonomy (GS-FR-038, GS-FR-039, GS-NFR-007)

### 7.1 `WorkflowLimits`

```text
WorkflowLimits
  max_turns                  integer > 0
  max_consecutive_failures   integer > 0
  inactivity_timeout_ms      integer > 0
  absolute_lifetime_ms       integer > 0
  max_in_flight_actions      1          # fixed; see dispatch.md §2
```

Limits are configuration, stored **on the record** at creation. Storing them per workflow rather
than reading global configuration at check time means a config change cannot retroactively extend a
workflow that is already running, and a restart cannot pick up a laxer bound than the one the work
started under (GS-NFR-007).

`max_in_flight_actions` is fixed at 1 and is not configurable. It is the one-event/one-action
invariant (GS-FR-024) expressed as a limit, and making it tunable would make that invariant a
setting.

These limits are also the **only** source of the response deadline Gist states to a bot.
`actions.md` §5.2 derives `response_deadline_ms` as
`min(inactivity_timeout_ms, remaining_lifetime_ms)` and dispatches nothing when that is not
positive. The deadline is therefore a projection of the stored limits, not a second, softer bound
living in the instruction — which is what §7.4 requires of anything that could otherwise read as an
extension.

### 7.2 Counting

- `turn_count` increments on every committed transition whose `source_event_key` is a new supervisor
  event. Internal bookkeeping transitions do not consume a turn.
- A continuation **is** a new supervisor event and consumes a turn like any other. This is not
  bookkeeping: it is how `max_turns` bounds the internal path as tightly as it bounds Slack traffic,
  so runtime-generated turns can never be the cheap ones (`actions.md` §2.2 rule 4).
- `consecutive_failures` increments on a dispatch failure, a bot-reported failure, or an internal
  error, and **resets to zero** on any committed transition into `running`, `reviewing`, or
  `completed`.

### 7.3 Reaching a limit (GS-FR-039)

| Limit reached | Next state | `OutcomeClass` |
|---|---|---|
| `max_turns` | `waiting_human` | — (set only if it later terminates) |
| `max_consecutive_failures` | `waiting_human` | — |
| `inactivity_timeout_ms` since `last_activity_at` | `timed_out` | `timeout_inactivity` |
| `absolute_lifetime_ms` since `created_at` | `timed_out` | `timeout_lifetime` |

Turn and failure limits stop and ask a human because the work may still be salvageable; timeouts
terminate because nothing is going to arrive. In no case does the workflow continue silently
(GS-FR-039).

A limit check happens **before** evaluation on every correlated event and again before every
dispatch. Checking only at dispatch time would let a bot-reply loop burn turns without ever
reaching a check.

### 7.4 Limits cannot be raised from the channel

No message, from any actor class including the owner, may raise a limit, extend a timeout, or reset
a counter by content (`identity.md` §4). An owner who needs more room cancels and starts new work,
or an operator changes configuration, which affects only workflows created afterwards.

Nor may **model output**. The response deadline Gist puts in an instruction is derived here
(§7.1), never supplied by the model: a model-chosen `response_deadline_ms` would have been an
extension arriving through a field that looked like part of the work rather than part of the policy.
`actions.md` §5 splits the instruction envelope so that field cannot be reached at all.
